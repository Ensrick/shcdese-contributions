# Deferred translation-hook startup

This source candidate moves only the three SDK-owned Translate.lookUpText detours from ManagedHookManager.Apply to the PRE side of the existing early Noesis.GUI.LoadComponent interception for MasterController. No new hook, readiness service, timer, polling or crash-report suppression is added.

## Initialization evidence and behavior

Actual installed Assembly-CSharp.dll BC8B6A39 has MasterController::.ctor call MainViewModel.INIT and set DataContext before InitializeComponent. INIT constructs and stores MainViewModel before returning; InitializeComponent calls GUI.LoadComponent. Activation therefore occurs after successful game-owned MainViewModel construction and before MasterController.xaml is loaded. It does not claim that FatControler.Awake has completed or that GlobalUIRoot is assigned; that store comes later. Translate's initialization tail uses MainViewModel.SetLocalisedLayout, whose current implementation changes the Japanese font size and does not use GlobalUIRoot.

The existing ApplyEarly path installs the Noesis load interception before Apply. Localization data registration and GameTranslateAPI's map-unload subscription stay in their existing startup locations. The original GUI call remains once, followed by the existing InjectBindings path. A startup failure does not skip that native/original flow. An original-load exception still propagates without postbinding; the existing postbinding exception isolation is retained.

The owned hook group uses the exact installed MonoMod HookConfig.ManualApply constructor contract. ManualApply is used to prevent executable activation before wrapper ownership is published; it is not assumed to prevent compilation or static initialization. All three handles and trampolines are prepared first, all wrapper fields are published with release writes, and only then are the three hooks applied sequentially. The exact provider's IsApplied is checked after construction, each Apply and each Undo; a provider veto is observed and reported rather than overridden or treated as success. Fallback callback reads acquire their wrapper. Lookup callbacks do not acquire the startup gate. Native activation is sequential, not an atomic three-hook transaction.

The private lifecycle gate excludes concurrent preparation/application and unload. Reentrant component loads do not reinstall; reentrant unload is terminal and checked after every preparation/application. Any returned handles are retained and rollback attempts each independently in reverse order. Failed or vetoed Undo is reported and ownership/trampolines are retained; the candidate does not claim cleanup succeeded after such a failure. Unload terminates and cleans this group before the other existing undo operations, so an unrelated undo failure cannot leave this group eligible for late installation. Rollback cannot undo already-returned text or external callback effects. Cleanup diagnostic failures fall back to the Unity log; bounded first-error references are retained even if both logging sinks fail, so a logging failure cannot stop remaining cleanup or legacy unload.

## Compatibility and migration

This is a material behavioral compatibility change. ManagedHookManager and Apply are public; previously a successful Apply synchronously installed translation detours. After this change those detours are available at the first qualifying MasterController load. Internal hook fields and delegates retain their names, types and accessibility, but same-assembly or reflection consumers observing them immediately after Apply may now see null. All existing public ManagedDetour signatures/properties and the existing immediate-apply constructor behavior remain unchanged. The added wrapper constructor is internal.

Consumers should register dictionary overrides through the existing GameTranslateAPI state APIs and use existing game event providers for their own operations. Those dictionary registrations remain early; consumers must not treat Apply return or internal hook fields as a new readiness contract. Original-text getters and localization-file loading can themselves touch Translate and are not made safe during arbitrary early plugin startup by this change. No replacement public ready flag/event is introduced. Release/version and maintainer review must explicitly carry this timing risk; passing one consumer set is not proof of compatibility for unknown consumers. The source is not installed or presented as runtime-ready.

## Adjacent source-backed gap

GameAssetModManager registers locale files before Apply. GameTranslateAPI.LoadLocalizationFile calls SaveTranslationSection, which reads Translate.Instance.SectionNames (current official lines247/253). That is another potential early static-initialization path if locale files are present. This candidate intentionally does not change that parser/registration behavior and must not be described as fixing all translation initialization. The full370-entry section map includes indices absent from the game enum, so substituting Enum.GetNames/ToString would change valid-section behavior. Qualifying a no-singleton section metadata contract is separate work. Direct early consumer original-text lookups remain another possible trigger.

## Qualification and limits

TranslationStartupChecks follows the existing contribution candidate/fixture/project and PASS-group layout. The successor compiles all five complete production files, including the genuine Manager private constructor, Apply, ApplyEarly and Unload. No extracted Apply/Unload or replacement decision model is compiled. Explicit unrelated void declarations/reflection targets are compile/control-flow leaves, not game ABI emulation. MonoMod, game, Noesis, localization registry, logging and unrelated hook slots are explicit controlled leaves. Cases cover early non-Master loads, PRE/POST ordering, three overload outputs/fallbacks, release/acquire ownership publication, another thread invoking a lookup during Apply, reentrant/concurrent unload, reentrant loads, per-stage failures and nonthrowing provider vetoes, retained ownership after Undo failure, and original/injection exception behavior.

The current MainViewModel constructor and its inspected startup callees contain no explicit Translate lookup/localized-string cache; collections use empty strings/enums and sprite setup reads image resources. Font and Noesis native/resource callbacks are not proven text-cache-free by that source scan. These fixtures do not load the game or perform executable detours, render XAML, establish initial text equivalence, identify the captured AV's ultimate handler, or prove a clean launch. Full current SDK build/link and another exact installed-candidate G0 with translation-output/first-UI checks remain required. The existing BR/animal failures and native crash reporting stay enabled.

The current whole-Apply fixture retains all fourteen groups. A local Windows x64 SDK 10.0.300 / .NET 10.0.8 run reproduced the one genuine eager-preparation failure in the mixed whole-Manager baseline wiring control and passed all fourteen candidate groups. Both binaries' CodeView/PDB identities and all seven source documents matched selected inputs. The baseline is not a full old SDK; prior partial-manager/admission-gap evidence is historical. Hosted CI for this portable project is pending. Full SDK/provider-link and installed-game claims remain unqualified.
